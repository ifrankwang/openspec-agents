> **项目规范优先**：本 skill 所列约定为推荐标准。若项目已有明确规范且与本 skill 不一致，以项目规范为准。
> 本文列出**最低基线**，不限于所列条目。判定时必须结合界面实际呈现做拓展覆盖，下列未列但同属「用户认不出状态」或「程序识别不到状态」的问题，同样按本节口径处理。

## DESIGN.md 的定位

DESIGN.md 是界面层的单一事实源，放在项目根目录，与 AGENTS.md 同层：

- AGENTS.md 管代码怎么组织：分层、命名、工程约定
- DESIGN.md 管界面长什么样：颜色、字体、间距、圆角、组件外观、状态怎么表达

有了它，界面判定有据可依，不必每次临时商量；没有它，同一产品的不同页面会各自发明一套视觉与状态写法。

DESIGN.md 是 Google 发布的开放格式规范（仓库 `github.com/google-labs-code/design.md`，当前 alpha）。一个文件由两部分组成：

1. **YAML 设计令牌**（机器可读）：文件顶部 `---` 包裹的 front matter，也可在各段落内以 ```` ```yaml ```` 代码块穿插；多个 YAML 块会合并成一棵令牌树，同一顶层键只能定义一次。
2. **Markdown 正文**（人读的理由）：按固定 8 段写，说明这些值为什么存在、什么时候用。

令牌是规范值，正文解释怎么用；两者冲突时以令牌为准。

## 文件结构

### 令牌（YAML front matter）

| 键 | 是否必备 | 内容 |
|----|----------|------|
| `version` | 否 | 当前固定写 `alpha` |
| `name` | 是 | 视觉体系名 |
| `description` | 否 | 一句话定位：面向谁、传达什么 |
| `omitted` | 否 | 刻意省略的段落或令牌组，可带 `reason`，避免校验器报缺失 |
| `colors` | 是 | 颜色令牌，至少要有 `primary` |
| `typography` | 是 | 字体层级令牌 |
| `rounded` | 否 | 圆角刻度 |
| `spacing` | 否 | 间距刻度 |
| `components` | 是 | 组件令牌：背景、文字色、圆角、内边距、尺寸 |

取值约定：

- 颜色：任意合法 CSS 颜色（hex、`rgb()`、`oklch()`、具名色），推荐 hex
- 尺寸：数字 + `px` / `em` / `rem`
- 字体层级：`fontFamily`、`fontSize`、`fontWeight`、`lineHeight`、`letterSpacing`、`fontFeature`、`fontVariation`
- 组件令牌可引用其他令牌，写作 `{colors.primary}`、`{rounded.md}`，必须指向具体值而非令牌组
- 组件合法属性只有：`backgroundColor`、`textColor`、`typography`、`rounded`、`padding`、`size`、`height`、`width`；悬停、按下、禁用等变体写成独立条目，键名与基名相关联，如 `button-primary-hover`

```yaml
---
version: alpha
name: Heritage
colors:
  primary: "#1A1C1E"
  tertiary: "#B8422E"
typography:
  body-md:
    fontFamily: Public Sans
    fontSize: 16px
    lineHeight: 1.6
rounded:
  sm: 4px
components:
  button-primary:
    backgroundColor: "{colors.tertiary}"
    textColor: "{colors.primary}"
    rounded: "{rounded.sm}"
    padding: 12px
---
```

### 正文的 8 个段落

段落用 `##` 标题，顺序固定；当前项目不适用的整段省略（并在 `omitted` 里登记）。段落若存在，必须按下列顺序出现：

| 顺序 | 段落（别名） | 写什么 |
|------|--------------|--------|
| 1 | Overview（Brand & Style） | 品牌气质、目标用户、界面该唤起什么感觉；具体规则缺失时的判断基准 |
| 2 | Colors | 每个颜色令牌的语义与使用场合，说明为什么是这个色 |
| 3 | Typography | 字体层级与各自职责（标题/正文/标签/数据的取用边界） |
| 4 | Layout（Layout & Spacing） | 栅格模型、最大宽度、间距节奏与分组原则 |
| 5 | Elevation & Depth（Elevation） | 层级怎么表达：阴影的扩散与颜色，或扁平界面改用边框与底色 |
| 6 | Shapes | 圆角语言与适用范围，说明锐利/圆润的取捨 |
| 7 | Components | 每个组件的外观与**状态清单**（见下节），状态承载方式必须写明 |
| 8 | Do's and Don'ts | 成对的可执行推荐与禁令 |

`Overview` 与 `Do's and Don'ts` 只写正文，不承载令牌；其余段落可只写正文或只放令牌，但两者都写时须一致。

### 校验

```bash
npx @google/design.md lint DESIGN.md                                   # 令牌引用、对比度、结构检查
npx @google/design.md diff DESIGN.md DESIGN-v2.md                      # 两版差异与回归判定
```

- 新增或修改 DESIGN.md 后必须跑 lint，错误清零、告警逐条判断；告警属于刻意设计时在 `omitted` 或正文里写明理由
- `diff` 用于视觉变更的影响面核对：令牌被改动而界面未同步，按「设计与实现脱节」处理
- 重复段落标题、重复顶层键会导致校验直接拒绝，必须改掉

## 状态语义规范

Google 的格式只规定令牌与美学，不规定状态怎么表达。本节是硬性补充：**每个可交互或可展示的字段，其状态必须同时满足两条——用户一眼能认出来，程序能识别。**

判断方法：把界面截图给一个没用过该系统的人，他能说出「这个必填」「这个不能点」「这个是空的」；同时读屏与自动化测试能从属性上分辨同一状态。两条缺一即不达标。

| 状态 | 视觉承载（用户一眼认出） | 程序承载（可识别） |
|------|--------------------------|--------------------|
| 必填 | 可见的必填标记：文字「必填」或图标，且不依赖颜色或灰度；不得只用 `*` 而不给图例 | `required` 或 `aria-required="true"` |
| 可选 | 与必填同一套标签样式，不得仅靠灰色文字、较浅字重表达「可选」 | 不声明必填属性 |
| 禁用 | 有可读的「为什么不可用」说明（旁注、悬浮提示或页面说明）；视觉降权只是辅助 | `disabled` 或 `aria-disabled="true"` |
| 只读 | 与禁用明显不同：文字保持正常对比度、可聚焦、无禁用光标 | `readonly` 或 `aria-readonly="true"` |
| 空数据 | 明确的空态文案（如「暂无数据」）+ 主操作入口（新建、清除筛选） | `role="status"` 或等价可播报机制 |
| 加载中 | 骨架、进度或「加载中」文案，且与空态外观可区分；布局不跳动 | `aria-busy="true"` 或可播报的状态文案 |
| 出错 | 字段级错误文案说明「错在哪、怎么改」，红色边框只是辅助；表单级汇总给出待改项 | `aria-invalid="true"` + `aria-describedby` 指向错误文案 |
| 危险操作 | 二次确认，写清影响范围与是否可撤销；确认按钮用具体动作文案（如「删除 3 个订单」）而不是「确定」 | 确认交互可获得键盘焦点，后果说明为可读文本 |

组合与边界：

- **状态不得只用颜色或灰度承载**。错误态、必填态、状态徽标、成功/失败提示，除颜色外必须有文字或图标 → 违反按 Medium；必填与可选仅靠灰度区分、禁用仅靠降透明度而不说明原因、空态与加载态同形，均按此条处理
- **禁用与只读不得互相冒充**：用禁用实现只读，或用只读实现禁用，都让用户与程序同时误判 → High
- **必填却不可编辑**（必填 + 禁用/只读）必须写明为什么必需却改不了；不写一律视为状态设计缺失 → Medium
- 同一字段不得同时挂互斥状态（禁用 + 只读、空态 + 加载中）；状态机要能收敛到唯一状态
- 状态文案写「为什么 / 怎么办」，不写「操作失败」「请输入正确内容」这类无信息量的话
- 同一组件在全项目的状态表达必须一致：一处用边框表示错误、另一处用图标，等于没有标准 → Medium
- 状态清单必须登记在 DESIGN.md 的 `Components` 段落：每个组件列出支持的状态与承载方式；实现与该清单不一致即为走样

## 反模式清单

1. **必填字段渲染成灰色文字 + 空心方块**：用户读成「可选、未勾选」，填不填都犹豫，最终提交被拦。正确做法是可见的必填标记 + `required`，且标签样式与可选字段一致，只有标记不同
2. **用自定义 `div` / `span` 拼控件替代设计系统组件**：丢失键盘可达、焦点样式、禁用与错误语义，读屏读不出控件类型；库未覆盖时先补共享组件，不在页面里就地造
3. **只有颜色的状态徽标**：绿点=成功、红点=失败，色盲用户与灰度截图都无法分辨；必须配文字或图标
4. **错误提示只变红不改文案**：边框变红但提示还是「请检查输入」，用户不知道改哪里；错误文案要定位到字段并给改法
5. **禁用只降透明度**：看得见点不了，也不知道为什么；必须给原因说明
6. **只读做成禁用，或禁用冒充只读**：前者让用户以为数据不可复制，后者让用户以为还能编辑
7. **空数据与加载中共用同一外观**：一直转圈的分不清是没数据还是没加载完；两者必须可区分且各有文案
8. **必填只用占位符或孤立的星号**：占位符输入后消失，孤立星号没有图例说明含义
9. **危险操作只标红、无二次确认**：撤销不了的删除一键生效；必须确认并说明后果
10. **DESIGN.md 与实现脱节**：令牌改了界面没改，或界面硬编码颜色/间距绕过令牌；视觉判定一律以 DESIGN.md 为准，改视觉同批改文件
11. **多个页面各自发明状态写法**：同一产品里禁用一处灰、一处删除线、一处直接隐藏，等于没有规范

## 何时产出与更新 DESIGN.md

- **首次出现用户可见界面时建立**：新增页面、表单、列表、弹窗、移动端或 H5 界面，只要用户会看到并操作，就要有 DESIGN.md
- **已有 DESIGN.md 时按其执行**：界面取值、组件外观、状态表达均以它为准，不得绕过令牌硬编码
- **视觉变更同批更新**：颜色、字体、圆角、间距、组件外观、状态承载方式发生变化时，在同一批改动里同步 DESIGN.md 与其令牌，不允许文件落后于实现
- **新增组件或新增状态先补规范**：新组件、新状态（如新增「部分成功」）先写进 `Components` 段落再实现；来不及先实现时，同批补齐
- **已有设计系统或组件库但缺 DESIGN.md**：从现有令牌与组件文档反推生成，暂不涉及的段落用 `omitted` 登记，不要凭空发明新值
- **纯后端、CLI、库项目不需要**：没有用户可见界面就不产出，避免制造与实现无关的文档
