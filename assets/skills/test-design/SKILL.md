> **项目规范优先**：本 skill 所列约定为推荐标准。若项目已有明确规范且与本 skill 不一致，以项目规范为准。

## 行为面推导

从 spec 与接口/数据契约推导本次变更牵动的行为面，作为覆盖的完整边界；禁止把验收标准的条目直接当成行为面清单：

- 业务规则：除 spec 与契约外，须从存量系统挖掘被本次变更复用或牵动的业务规则——既有实现的分支与校验、数据库约束与索引、配置常量与开关、领域模型不变量、历史缺陷记录；每条业务规则标注来源（spec 条目/代码位置/数据库约束/配置项）。本变更新增或修改的规则以 proposal 的规则边界结论与 spec 的各类场景为输入
- 业务流程与链路：本次变更牵动的跨步骤、跨接口业务流程——一条链路从一个真实入口起步，串联多个动作，最终落在可观察结果上。来源为 spec 场景、proposal 的关联场景与实施逻辑、历史缺陷记录（同一缺陷的再次出现往往是新链路的信号）。每条链路须拆出四个要素：入口（用户或下游实际触发的那个动作）、步骤顺序（各步按什么次序执行、顺序换了结果是否不同）、前置状态（链路执行前数据必须处于什么状态）、最终可观察结果（链路跑完后能查到的持久化状态与字段内容）。同一份数据存在多条写入路径时（导入、保存、更新、批量同步），写入路径的先后作用本身就是链路要素，须单独成条
- 状态与流程：新增/变更的状态、状态流转路径、初始态与终止态
- 数据承载：新增/变更字段、字段的产出与读写位置、可空性、默认值
- 枚举与取值域：有限取值集合、类别标记、字典项
- 权限与可见性：谁能调用、越权访问的拒绝路径
- 外部依赖：第三方与下游调用、超时与失败路径
- 可选路径：可选字段、可选分支、可跳过的步骤
- 异步产出：延迟落库、消息入队、下游消费

行为面条目多于验收标准条目属正常：一条验收标准常牵动多条行为面。

## 用例矩阵

每条行为面至少覆盖三类，缺一类即覆盖不全：

| 类别 | 取值与场景 |
|------|-----------|
| 正常 | 按契约传入合法值，断言响应结构与关键产出 |
| 边界 | 空值/空集合/零、极值、超长、边界长度、类型非法、精度与舍入、日期与时间边界 |
| 异常 | 非法状态跳转、重复提交与幂等、并发、事务回滚、部分失败、依赖不可用与超时、越权访问 |

组合与状态迁移：按「规则 × 状态 × 外部事件」三轴收敛组合——多个可选字段或条件并存时按判定表收敛，并交叉展开规则命中、对象当前状态与外部事件（依赖回调、延迟任务、并发请求等）的组合格；交叉格与状态机的非法迁移成对覆盖，非法迁移须断言被拒绝。

链路轴与上述三轴的关系：三轴描述「单个动作在什么条件下发生」，是同一动作内部的组合维度；链路轴是它们之外的一条独立轴，描述「多个动作按什么顺序串起来」，不替代也不重复三轴。实现方式是在三轴给出的用例之外，再按链路清单逐条列出「链路 × 状态/顺序」的组合格——同一条链路在正常前置状态、临界前置状态、以及步骤顺序颠倒或重复时各取一格，每格落到具体用例名。两套轴打架的典型形态是：把链路拆成三个单动作分别塞进三轴矩阵、格子里看不到顺序——这等于没有链路覆盖。

链路组合格至少覆盖：链路正常顺序跑通、链路在某一步的前置状态不满足（如后续接口导入的数据已被前一接口补过默认值）时的行为、同一链路重复执行（幂等与重算语义）。

## 断言强度

- 每条行为至少一条「实现写错就红」的断言：断具体值、状态流转结果、副作用是否发生，而不是「没报错」
- 仅断言响应成功、字段非空、流程跑通，不构成断言
- 同一请求内一并发生的多个行为逐个断言，禁止以其中一个行为的断言替代其余
- 链路组合场景须断言最终持久化状态与字段内容：链路跑完后回查数据，逐字段核对值与前序步骤写入的值一致（含默认值、派生值、状态标记），不得以链路中各步接口返回 2xx 替代
- 断言范围包括连带效果：状态落库、消息入队、下游可消费、产出字段落位与完整性、缓存命中与失效、缓存与持久化数据的一致性

## 用例与实现解耦

- 预期值来自 spec 与契约，不得先运行实现再把实际结果抄成期望
- 禁止 mock 被测对象本身；替身只用于外部依赖
- 用例只依赖契约与可观察行为，不依赖实现内部结构（私有方法名、内部字段）

## 反向探针

取至少一条关键用例做对抗校验，证明用例真能发现问题：

1. 把实现改坏（拔掉被测行为、翻转判定条件、让产出落错位置）
2. 确认该用例失败
3. 原样还原实现
4. 全量用例复跑全绿，并确认工作区无残留改动（git status 干净）

探针内容禁止提交，不得保留任何痕迹。记录探针的改坏点、变红的用例、还原确认结果。反向探针未通过的用例视为无对抗力，须重写。

缺陷修复类变更的探针：把缺陷的触发条件（前置状态 + 操作顺序）固化为回归用例后，须确认该用例在修复前的实现形态上会失败——按探针四步，先把修复改回缺陷形态（还原缺陷分支、去掉重算逻辑、恢复旧判定条件），确认回归用例变红，再恢复修复并复跑全绿。只认「修复前红、修复后绿」这一条判据：如果回归用例在缺陷形态下仍然绿，说明它没有钉住缺陷，须重写。

禁止按修复后的实现反写期望值——先跑通修复版再把实际结果抄进断言，会让用例在任何实现下都绿，等于没有回归保护。期望值只能来自 spec 与缺陷现象（修复后应当得到什么）。

## 证据形态

| 交付物 | 要求 |
|--------|------|
| 行为面清单 | 按上节维度列出，标注对应验收标准，且标注每条规则的来源；流程链路须拆到入口 / 步骤顺序 / 前置状态 / 最终可观察结果四要素 |
| 用例矩阵 | 行为面 × 类别 → 用例名/脚本名，每格注明断什么；含规则×状态×外部事件交叉格与链路×状态/顺序组合格 |
| 探针记录 | 改坏点、变红用例、还原确认结果；缺陷修复类变更另记「缺陷形态下回归用例变红」的确认结果 |

## 适用范围

有代码、接口契约或数据口径变更时必须执行；纯文档、纯格式与注释变更不适用。
