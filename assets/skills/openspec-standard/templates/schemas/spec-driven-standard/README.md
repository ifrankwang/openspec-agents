# OpenSpec Schema: spec-driven-standard

通用 spec-driven 工作流模板：clarify → proposal → specs → design → tasks，
增强三点：
1. **clarify 前置门槛 + 关联场景清点 + 规则边界推演**：每次变更先做需求澄清
   与关联场景清点（首轮提问前枚举变更触及能力的全部消费方——功能入口 /
   共享处理逻辑 / 数据流下游，附代码证据；每个清点条目在访谈中经用户划界
   确认——纳入本 change 统一适配或排除附理由；同一数据存在多条落库路径时
   各路径校验与处理逻辑的一致性为必问分支；共享处理逻辑变更须与其全部消费
   入口同一 change 统一适配）；规则边界推演与清点分工：清点管「谁受影响」，
   规则边界推演管「判定条件本身站不站得住」——凡新增/修改业务规则、校验或
   拦截逻辑，或新增/改变任何执行路径的变更，须逐条推演该拦的条件与例外、
   功能上合法却会被误伤的合法反例（各对应 spec 一条「应当放行」场景）、同一
   业务意图的等价执行路径与判定挂载点（判定挂在业务意图层的动作上，不得落在
   被其它业务流程复用的底层动作上），并逐条核对新路径下既有规则是否仍该生效；
   结论落进 proposal 的「规则边界」小节与 spec 的应当拦截 / 应当放行 / 等价
   执行路径三类场景，其余变更写「不适用」+ 一句理由；跨接口业务链路另作第四类
   强制场景——须写成一条可测试的完整链路（WHEN 写清操作顺序，THEN 写清后续
   查询返回的字段内容并逐字段列明），按端点拆成多条不算满足；访谈穷尽后、写任何
   文档之前，主代理必须先向用户汇报结构化方案摘要（按要素清单逐项编号展开：
   一句话做什么 + 变更内容人话
   逐条列明（形如「导出功能新增「状态」字段」，视需要说明字段来源等
   背景）+ 是否动契约 + 选定方案与备选取舍 + 人话分步实施逻辑 +
   关联链路划界结论 + 规则边界推演结论 + 影响的能力面）并取得用户明确确认（HARD-GATE：摘要须以普通消息呈现，禁止用提问
   工具发起确认，访谈中的问答不视为确认；访谈未穷尽禁止呈现方案求确认，
   轮次中每题附的推荐答案不视为方案），确认记录落在 clarify.md，后续文档
   不得偏离。proposal.md 单列「实施逻辑」小节，以人话分步讲清怎么做（禁
   代码级名词，契约事实除外），代码级细节归 design.md。
2. **主代理访谈直录 + 分级撰写 + 提案期架构审查**：主代理亲自访谈，决策
   结论直接记入 clarify.md（访谈阶段唯一落笔的文档，不设独立访谈文件；
   只记最终结论，被取代时原地更新）；
   架构方向经用户确认后，按复杂度分级产出其余文档（proposal → specs →
   design → tasks，不逐文档分派）——简单变更由主代理本人按依赖顺序撰写
   （省 token），复杂变更派发唯一一个独立生成子代理在同一会话内撰写（保
   主代理上下文精简），分级判定与理由记入 clarify.md；文档齐备后由主代理
   派发独立架构审查子代理（全新会话，绝不复用生成子代理；优先项目可用的
   专用架构审查子代理，环境没有时用通用子代理；无论专用与否都注入随标准
   安装的 `agents/architecture-review.md` 全文作任务说明，专用子代理同样
   以其职责为准）做架构审查：结构校验
   （`openspec validate --strict`）、跨文档一致性、用户已确认架构方向的
   合理性、design 架构合规（按能力类别加载架构类 skill，不硬编码 skill 名）、
   规则边界推演核对、关联场景覆盖核对、与主 specs 交叉核对，并产出按任务组
   的执行边界（allowed_directories / allowed_packages / notes，机器可读）；
   发现问题由主代理本人修复后再次复核，循环最多 3 轮，复核干净通过（PASS）
   才算完成；issue 涉及变更用户已确认的架构方向时必须回到用户重新确认
   （重走方案确认门），不得静默覆盖；PASS 后主代理删除 `.review/` 并把执行
   边界写入 clarify.md 的「执行边界」小节（实施流程初始化时读取，缺失时按
   整个 worktree 处理）。完整三阶段编排契约写在 clarify 的 instruction
   里——这是主代理必读的一份，复核派发由此可达；复杂变更的生成子代理
   最终汇报必须提示主代理进入架构审查阶段，双保险防契约断链。
3. **自包含方法论**：决策树逐轮访谈（frontier 机制）全文内联在 clarify
   instruction 的 Methodology 节，不依赖任何外部 skill。

## 目录

```
openspec/schemas/<schema-name>/
├── schema.yaml    # 流程与文档结构定义（纯通用，无项目内容）
├── templates/     # 各文档模板（纯通用）
├── agents/        # 随标准安装的子代理职责文本（提案期架构审查）
└── README.md      # 本说明
```

配套文件（一并安装）：项目根 `openspec/config.yaml`（通用流程规则）。

## 接入新项目

**方式一（推荐，插件一键初始化）**：安装了 openspec-agents 插件的 AI 编码
工具中，在目标项目的常规主代理会话里说一句「初始化 openspec 提案标准」，
即自动写入本 schema 目录与配套 `openspec/config.yaml`；已初始化的项目重跑
即升级到最新标准（项目自定义 rules 条目与 context 保留）。

**方式二（手动回退，无插件环境）**：
1. 把本目录整体 copy 到新项目 `openspec/schemas/spec-driven-standard/`。
2. 把通用版 `openspec/config.yaml` copy 到新项目，确认 `schema:` 指向
   `spec-driven-standard`。
3. 在新项目 `AGENTS.md` 中写清项目特化约束（见下节），并确认每次变更的
   `.openspec.yaml` 的 `schema:` 字段指向正确。

> 生成子代理（复杂变更时）与提案期架构审查子代理会被指示读取项目
> `AGENTS.md` 与 `openspec/config.yaml`，因此项目特化约束写在 `AGENTS.md`
> 即可自动生效，schema 本身无需改动。

## 项目特化约束清单（写进 AGENTS.md 的内容）

| 类别 | 示例 |
|---|---|
| 技术栈 | 语言/框架/版本、构建工具、依赖管理 |
| 分层架构 | 分层/包组织、依赖方向、层间规则 |
| 领域约定 | 确定性 vs 不确定性分工、领域模型规范 |
| 数据库约定 | 表前缀、主键策略、审计字段、逻辑删除、迁移方式 |
| 质量门 | 格式/静态检查工具、测试策略、覆盖率门槛 |
| 方法论 | 澄清/评审/开发流程约定（如 TDD） |

## 三层分工（不重复原则）

| 位置 | 承载内容 | 例子 |
|---|---|---|
| `schema.yaml` instruction | 生成方法论与文档格式要求（官方方法论为底） | 场景标题 4 个 #、SHALL/MUST、ADDED/MODIFIED/REMOVED、四类强制场景（规则边界三类 + 跨接口业务链路）、任务组格式、每组自带测试与质量门、测试随实现同组、关联场景清点维度与单仓变更范围、实施逻辑小节、规则边界推演维度与三问 |
| `openspec/config.yaml` rules | **仅** schema 未覆盖的项目补充规则 | MODIFIED 终态契约表述、同语义一条需求、前置 change 标注格式、契约变更详列、访谈门与用户确认门、方案摘要结构、跨仓拆分边界、规则边界门禁口径（结论必列、三类场景、判定挂载点）、跨接口业务链路场景门禁 |
| 项目 `AGENTS.md` | 项目特化约束 | 技术栈、分层架构、数据库约定、质量门工具、方法论 |

`agents/architecture-review.md` 是提案期架构审查职责的单一事实源（角色、
输入、职责清单、定级口径、只报不改、输出格式、执行边界输出格式、skill
加载规则），随标准安装；schema instruction 只引用它、不复制其内容。方案
文档视角的定级口径与编排流程架构维度判例一致，不另立一套。

同一规则只写一处：通用生成方法论以 schema instruction 为准，config.yaml
rules 只写项目补充与阶段级强制项；确需两侧同时出现的强制项（如「禁止纯验证组」
「测试随实现同组」「单仓变更范围」）保持措辞一致，禁止再复制到第三处；
schema 不写项目专属内容。新增规则时先查上一层的 instruction 是否已覆盖。

官方升级 `openspec update` 会覆盖 `.agents/skills/` 下的 skill，本 schema
与 config.yaml 不受影响；CLI 升级后可重新对齐官方 `spec-driven`
（`openspec schema fork`）再叠加本模板的增强段落。
