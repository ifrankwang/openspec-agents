> **项目规范优先**：本 skill 所列约定为推荐标准。若项目已有明确规范且与本 skill 不一致，以项目规范为准。

## 构建命令

```bash
mvn verify                            # 全量验证（单次覆盖全部质量检查）
mvn spotless:apply                    # 自动格式化
mvn compile                           # 编译
mvn test                              # 运行测试
```

- `mvn verify` 为全量验证命令，单次执行即覆盖编译、测试、spotless:check、pmd:check、JaCoCo 覆盖率。构建成败以 `mvn verify -q; echo "BUILD_STATUS=$?"` 的退出码为唯一判据，不依赖肉眼从输出尾部寻找 BUILD SUCCESS/FAILURE 行（`-q` 静默模式抑制 INFO 级 BUILD 行，输出过长时尾部亦不可靠）
- 确认结果时禁止重复执行同一构建命令，单次执行已覆盖全量质量检查；修复后复验属正常重跑
- 需要抽查输出细节时使用非 `-q` 形态 + `grep -E "Tests run|ERROR|jacoco|spotless|pmd"` 提取关键行，禁止仅以 `tail`/`head` 截断输出导致结论行丢失后重跑

## 代码质量工具

**Spotless**（Palantir Java Format）：
- 提交前执行 `mvn spotless:apply` 格式化，`mvn spotless:check` 必须通过
- 配置在 pom.xml `spotless-maven-plugin`

**PMD**：
- 规则集定义按项目级 pmd-rules.xml

**SonarLint**：IDE 建议安装 SonarLint 插件，尽量修复提示问题

## 测试规范

**命名规范**：
- 测试类：`{ClassName}Test`（如 `OrderServiceTest`）
- 测试方法：`test{MethodName}`（如 `testCreateOrder`）

**分层策略**：
- Domain service 测试用纯 JUnit，零 Spring 依赖（domain 层本就无框架依赖）
- 优先切片测试 + `@Import` 组装所需 Bean，避免滥用全量 `@SpringBootTest`（启动慢、依赖环境）
- 仅跨多层集成测试时才用 `@SpringBootTest` + `@ActiveProfiles("test")`

**测试数据库**：
- 默认 H2 内存库（`MODE=PostgreSQL` 兼容模式）
- 配置见 `src/test/resources/application-test.yml`

**WireMock**：
- Stub 位置：`src/test/resources/mock/mappings/`
- 响应体位置：`__files/`
- 用于模拟外部 HTTP 服务

**ArchUnit**：
- 验收 Domain 层零框架依赖
- 验收层间依赖方向（interfaces → application → domain ← infrastructure）
- 依赖：`archunit-junit5`

**测试数据**：
- XLSX 测试文件 → `src/test/resources/`
- 配置文件 → `application-test.yml`

## 提交规范

使用 [Conventional Commits](https://www.conventionalcommits.org/)：
```
feat(domain): 新增 Xxx 值对象
fix(infra): 修复 N+1 查询问题
refactor(app): 重构 XxxService
test(domain): 补充 DomainRuleEngine 测试
docs: 更新 AGENTS.md
chore: 升级依赖版本
```

提交粒度：每个独立子任务至少一个 commit；修复审查反馈时 commit message 引用审查报告问题编号。

## 新功能开发

- 编写单元测试覆盖全部验收条件，测试先行
- 实现代码使测试通过，保持最小实现
- 重构消除重复、改善可读性，测试须持续通过

- 从问题表象逐层追溯根因，基于事实定位系统性根因
- 修复方案针对根因而非表象
- 编写回归测试覆盖该场景

- 使用日志框架输出，禁止直接输出到标准输出
- 任务完成前清理所有仅为调试目的添加的日志

## 事务与并发

- 事务边界在应用层显式声明：用例方法上标事务（`@Transactional`），而不是依赖调用链上某个上游方法恰好开了事务；边界不清按缺陷处理
- 传播行为与隔离级别显式指定（`propagation` / `isolation`），不依赖框架默认值；用默认值时须能说明默认值正好是想要的语义
- 禁止在事务内发起远程调用、消息发送、文件上传等长耗时外部操作：事务里等外部 IO 会长期持有数据库连接与锁（锁等待放大、连接池耗尽）
- 写操作需明确幂等键或去重机制（业务唯一键、唯一索引、幂等令牌、状态机前置校验），防重复提交与重试放大；既无幂等键也无去重机制即为缺陷
- 并发更新需选择乐观锁或悲观锁并说明理由：乐观锁用版本号或条件更新（`UPDATE ... WHERE version = ?`）并处理更新失败分支；悲观锁用行锁并说明锁范围与持有时长
- 禁止无保护的读-改-写：先查再改、中间无锁且更新无条件，按并发缺陷处理
- 跨聚合或跨服务的一致性必须明确用补偿、最终一致或事务消息，并说明失败回补路径；禁止「两边都写、出问题对账」这种隐式假设
- 事务内只做必要的写：参数校验、远程取数、大量计算放在事务外准备，缩短事务时长
- 同类内自调用（`this.method()`）不走代理，事务不生效；需要独立事务边界时拆到另一个 Bean，自调用导致事务失效按缺陷处理

## 消息与缓存一致性

- 本地事务提交后再发消息，或使用事务消息 / outbox（本地消息表）保证「提交 + 投递」原子；禁止事务未提交就投递（事务回滚后消息已发出）
- 消费端必须幂等：以消息唯一标识去重（去重表、唯一索引、业务幂等键），禁止假设消息只投递一次
- 消费失败的重试与兜底需明确：重试次数、退避策略、死信队列或补偿任务；无限重试与静默丢弃都不接受，无死信兜底即为缺陷
- 缓存与持久化的更新顺序需明确：先更库再删缓存（或双删），禁止「先删缓存再更库」，禁止只更库不清缓存（脏数据长期不失效）
- 缓存删除失败须可观测（日志与指标）且有补偿，不静默失败
- 需说明缓存击穿、穿透、雪崩的防护口径：热点 key 互斥重建或逻辑过期、空值缓存或布隆过滤、过期时间加随机抖动；无防护且无说明即为不满足
- 缓存 key 集中定义：前缀、命名规则、版本标识统一，禁止散落拼 key；缓存结构变更按新 key 版本发布，避免旧结构被新代码读到
- 本地缓存与分布式缓存并存时须说明一致性与失效传播方式

## 可观测性

适用于已接入监控平台的项目。

- 日志使用统一级别并带结构化字段：至少包含链路标识与业务标识（业务单据号、用户标识的脱敏值）；禁止只打一句字符串、禁止字符串拼接破坏结构化
- 级别口径统一：`error` 只用于需要人介入的异常（带堆栈），`warn` 用于可自愈的降级，`info` 用于关键业务节点；异常记在 `info`、每个请求都刷 `error` 均属级别误用
- 关键路径需有延迟、错误率、饱和度指标：接口耗时（分位值）、失败计数、连接池 / 线程池 / 队列水位；只记日志不记指标即为不满足
- 跨服务调用需透传链路标识：入站从请求头提取、出站注入，异步场景（线程池、消息消费）同样传递；透传断裂即为不满足
- 关键指标需有告警阈值与责任人：阈值有依据（基线或 SLO 目标），告警有人接并有处置口径；只配告警不写责任人即为不满足
- 健康检查端点需反映依赖可用性而非仅进程存活：数据库、缓存、外部依赖的可用状态纳入检查项，并区分存活与就绪两类探针

## 发布与回滚

适用于已有发布流水线的项目。

- 发布前需确认数据库迁移脚本向前兼容：旧代码能在新结构上运行（加字段给默认值或可空、不改字段语义、不删列、不重命名），保证发布过程中新旧实例并存不炸
- 迁移脚本必须可回滚，或明确说明为什么不可回滚及对应的兜底方式（备份恢复、只增不删的演进式变更）
- 需要灰度或分批发布时说明分批依据（按实例 / 按流量 / 按用户 / 按区域）、观察指标（错误率、延迟、业务成功率）与放量条件
- 需明确回滚触发条件：错误率、延迟、业务指标偏离阈值的具体数值，而不是「看情况」；同时写明谁执行、回滚到哪个版本
- 回滚后的数据兼容处理：新代码写入的新字段 / 新结构在回滚后仍可被旧代码接受（只增不删、双向可读），不可兼容时须给出补偿脚本
- 多服务契约变更按依赖顺序发布：先加字段再消费、先双写再切换，禁止要求所有调用方同时升级

## Spring Boot 启动与配置

**启动命令**：`mvn spring-boot:run` 或 `java -jar`

**健康检查**：`/actuator/health`（需引入 actuator starter）

**配置文件分层**：
- `application.yml` — 公共配置
- `application-dev.yml` — 开发环境
- `application-prod.yml` — 生产环境
- `application-test.yml` — 测试环境

**文件上传**：`spring.servlet.multipart.max-file-size: 20MB`，Controller 层须做文件类型白名单校验

**CORS**：开发环境允许前端跨域
