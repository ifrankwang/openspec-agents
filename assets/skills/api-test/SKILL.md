> **项目规范优先**：本 skill 所列约定为推荐标准。若项目已有明确规范且与本 skill 不一致，以项目规范为准。

## 覆盖模型

接口测试的覆盖单元是业务链路，不是接口本身。链路指从一个真实入口起步、按业务顺序串联多个接口、最终落在可观察结果上的完整业务流程；对单个接口发一次请求断言其响应，属于单接口单元测试，不构成接口测试。

以导入场景为反例：接口 A 导入数据时补了一批默认值，接口 B 再导入同一份数据时没有重算，两个接口分别单测都通过，链路仍然错。链路用例才覆盖这类跨接口的顺序作用——前一个接口写入的状态是否被后一个接口如实承接或重算。

## 目录结构

API 测试素材独立于项目源代码目录（不放入 src/test/ 等构建工具测试源码目录），避免与单元测试混淆。

```
<project-root>/api-tests/
  ├── data/        # SQL 前置数据脚本（按场景准备数据库数据）
  └── script/      # API 测试脚本
```

目录位置可据项目现有惯例微调，但必须与构建工具的测试源码目录隔离。

## 脚本格式

API 测试脚本使用 IntelliJ IDEA HTTP Client（.http 文件）格式。每个场景以 `###` 分隔。

### 脚本组织

脚本按业务链路组织：一个 `.http` 文件对应一条链路（或一组同源链路），文件内用 `###` 块按业务执行顺序排列该链路的各个步骤。每个 `###` 块头部注明溯源场景（该步骤对应 spec 的哪条场景或哪条历史缺陷），使脚本可回溯到需求。

禁止「一个接口一个脚本」：按接口切文件会把同一条链路拆散到不同文件、丢失执行顺序，等于退回单接口单元测试。接口基础面用例作为附属块并入其所属链路的文件（无链路归属时单列一个基础面文件）。

### 跨接口链路示例

以「创建订单 → 列表检索 → 详情核对」为例，演示跨 `###` 块的变量传递：前一个请求的响应字段命名成变量，后续块用 `{{变量}}` 引用；断言落到字段值，不停在状态码。

```http
### 链路 CREATED-ORDER-LIST-001 / 步骤1：创建订单（溯源 spec: 订单创建场景）
# @name createOrder
POST {{BASE_URL}}/api/v1/orders
Content-Type: application/json
Authorization: Bearer {{TOKEN}}

{"orderNo": "SO202608140001", "customerName": "华东供应链", "amount": 12800.50, "status": "CREATED"}

> {%
    client.test("创建订单返回 201", function() {
        client.assert(response.status === 201, "期望 201，实际 " + response.status);
        client.assert(response.body.data.orderNo === "SO202608140001", "订单号回显不一致");
    });
    // 把后续步骤要用的标识存成脚本变量，供下方 ### 块引用
    client.global.set("ORDER_ID", response.body.data.id);
    client.global.set("ORDER_NO", response.body.data.orderNo);
%}

### 链路 CREATED-ORDER-LIST-001 / 步骤2：列表检索能查到刚创建的订单（溯源 spec: 订单列表场景）
# 变量传递：步骤1 写入的 {{ORDER_NO}} 在本块请求与断言中复用
GET {{BASE_URL}}/api/v1/orders?orderNo={{ORDER_NO}}
Authorization: Bearer {{TOKEN}}

> {%
    client.test("列表能检索到刚创建的订单", function() {
        client.assert(response.status === 200, "期望 200，实际 " + response.status);
        client.assert(response.body.data.total === 1, "期望命中 1 条，实际 " + response.body.data.total);
        const row = response.body.data.records[0];
        // 逐字段核对：后续接口查到的值必须与前序接口写入的值一致
        client.assert(row.orderNo === "SO202608140001", "列表订单号不一致：" + row.orderNo);
        client.assert(row.customerName === "华东供应链", "列表客户名不一致：" + row.customerName);
        client.assert(row.amount === 12800.50, "列表金额不一致：" + row.amount);
        client.assert(row.status === "CREATED", "列表状态不一致：" + row.status);
    });
%}

### 链路 CREATED-ORDER-LIST-001 / 步骤3：详情字段逐项核对（溯源 spec: 订单详情场景）
# 变量传递：{{ORDER_ID}} 来自步骤1 的响应体
GET {{BASE_URL}}/api/v1/orders/{{ORDER_ID}}
Authorization: Bearer {{TOKEN}}

> {%
    client.test("详情字段内容与创建入参逐项一致", function() {
        client.assert(response.status === 200, "期望 200，实际 " + response.status);
        const data = response.body.data;
        client.assert(data.orderNo === "SO202608140001", "详情订单号不一致：" + data.orderNo);
        client.assert(data.customerName === "华东供应链", "详情客户名不一致：" + data.customerName);
        client.assert(data.amount === 12800.50, "详情金额不一致：" + data.amount);
        client.assert(data.status === "CREATED", "详情状态不一致：" + data.status);
    });
%}
```

变量传递的三条要求：命名用业务语义（`ORDER_ID`、`IMPORT_BATCH_NO`，不用 `var1`）；变量必须来自本次链路前序步骤的真实响应，不得在环境文件里硬编码期望值；后续块的断言必须引用前序写入的字段值，而不是重复一遍字面量——否则链路退化成互不相干的两段。

### 接口基础面示例

基础面用例补单接口的入参与错误处理，可作为独立块并入同一文件：

```http
### 基础面：创建订单缺必填字段（缺 orderNo）
POST {{BASE_URL}}/api/v1/orders
Content-Type: application/json
Authorization: Bearer {{TOKEN}}

{"customerName": "华东供应链"}

> {%
    client.test("缺必填字段返回 4xx", function() {
        client.assert(response.status >= 400 && response.status < 500, "期望 4xx，实际 " + response.status);
    });
%}

### 基础面：创建订单非法值（orderNo 为空串）
POST {{BASE_URL}}/api/v1/orders
Content-Type: application/json
Authorization: Bearer {{TOKEN}}

{"orderNo": "", "customerName": "华东供应链"}

> {%
    client.test("非法值返回 4xx", function() {
        client.assert(response.status >= 400 && response.status < 500, "期望 4xx，实际 " + response.status);
    });
%}
```

## 旧脚本迁移

若 `api-tests/script/` 目录已存在 shell（`.sh`）+ curl + jq 旧版脚本，转为 `.http` 格式：
- 每个 `curl` 命令及其 headers 和 body 转为一条 `###` 分隔的请求
- 状态码和字段校验的 shell 断言（`jq` + `if`）转为 `client.test()` + `client.assert()`
- Shell 变量（如 `BASE`, `TOKEN`）转为 `{{ }}` 环境变量，来源写入 `api-tests/http-client.env.json`
- 迁移后删除 `.sh` 文件，不留残余

链路口径同样适用于迁移，但迁移范围限于本次 change 涉及的脚本：落在 change 范围内的旧脚本按业务链路重组（同一链路的请求并进一个文件、按执行顺序排列），change 范围外的存量脚本保持原样不动，不以「顺手重组」扩大本次变更范围。

## SQL 前置数据脚本

SQL 脚本按场景准备无法通过接口构造的数据库数据（历史数据状态、多表联动前置条件）。要求幂等：

- PostgreSQL: `INSERT INTO ... ON CONFLICT DO NOTHING`
- MySQL: `INSERT IGNORE INTO ...`
- H2: `MERGE INTO ...` 或 `INSERT ... ON CONFLICT DO NOTHING`

按项目实际 DB 类型选择写法。

## 后置校验

目的：把断言从响应层升级到数据承载层，在接口调用后校验数据库状态、缓存命中与键值、消息入队与下游消费；仅凭响应状态码与响应体不构成验收。

- 只读通道：使用数据库只读查询与缓存只读查询作为后置校验手段，禁止任何写操作（含为校验而临时插数、改状态、删键）
- 隔离实例：必须查本次变更按「执行顺序」隔离启动的实例，禁止查询宿主既有的数据库与缓存；隔离标识与建议端口同来自编排会话上下文
- 异步或延迟产出：等待产出完成后断言，须写明超时口径（最长等待时长与轮询间隔），超时仍未产出即判失败，不得以「稍后再查」放行
- 断言口径：数据库断言落到具体字段值与记录数；缓存断言区分命中/未命中并核对键与值；消息断言核对入队与下游消费结果
- 客户端命令按项目技术栈确定，本节只定方法与断言口径，不在本文件写死具体客户端与命令

## 认证发现

API 测试脚本运行前需获取有效认证凭证。常见模式：

1. **Dev-only login 端点**：检查项目配置中是否有 profile 专属的免登入口（如 local/dev profile 下的登录 API）
2. **静态 Token**：检查项目是否有 dev profile 专属的 JWT 密钥配置，可用相同密钥签发测试 token
3. **Basic Auth**：检查项目安全配置中 dev profile 是否有固定凭证或免登入口
4. **无认证**：若 dev profile 完全关闭认证，无需 token

从项目配置文件和安全配置类中查找。

## 执行顺序

```
1. **MUST** 启动基础设施（Docker compose 项目名带隔离标识：`docker compose -p <namespace> up -d`，避免与并发 change 的容器冲突；隔离对象不限于数据库——mock 服务、消息队列/缓存等中间件、扫描分析平台等一切为本变更启动的资源均须经隔离标识启动，禁止复用宿主既有实例或共享端口）
2. **MUST** 准备 SQL 前置数据（写入本 change 的隔离容器内 DB）
3. **MUST** 启动服务（端口用编排会话建议端口：`--server.port=<建议端口>`，避免并发 change 端口冲突），启动后记录服务进程 PID，并确认实际监听端口与会话建议端口一致；不一致视为启动失败，修正端口参数重新启动，禁止让服务落回项目默认端口
4. API 测试脚本（BASE_URL 使用上述端口）
5. **MUST** 停止服务并清理隔离环境（`docker compose -p <namespace> down`），随后幂等自检：本 change 隔离标识下无残留容器（`docker compose -p <namespace> ps` 为空）、本变更记录的服务进程已退出且隔离端口（建议端口）无进程监听；自检中发现无法确认归属本变更的进程（工作目录不在本变更工作目录内）禁止清理，在结果中标注说明
```

以上第 1、2、3、5 条为 MUST：隔离（独立 compose 项目名、隔离数据库、隔离 mock 服务/中间件/扫描分析平台、建议端口、down 清理）是并发安全硬约束，不适用本文件开头「项目规范优先」的推荐豁免。

- SQL 在前：先准备数据，再启动应用确保应用启动时读取到完整数据
- 隔离标识 `<namespace>`、建议端口与本变更工作目录同来自编排会话上下文
- 隔离对象不限于数据库：除数据库外，mock 服务、消息队列/缓存等中间件、扫描分析平台等其余为本变更启动的环境资源均须按隔离标识隔离；仅隔离数据库不满足并发安全要求
- 启动服务：按项目构建文件确定的启动方式（mvn / gradle / npm 等），端口用编排会话建议端口
- API 脚本：BASE_URL 使用上述建议端口，依赖运行中的服务
- 停止服务：测试完成后停止服务并清理隔离环境

## 覆盖要求

覆盖对象是本次 change 涉及的业务链路清单（主体）加接口基础面（补充）：

| 覆盖面 | 覆盖内容 |
|------|---------|
| 业务链路 | 从本次 change 的 spec 场景、proposal 的关联场景与实施逻辑、历史缺陷记录枚举出业务链路清单；每条链路从一个真实入口起步（用户实际触发的接口、导入入口、定时任务或消息触发），按业务顺序串联多个接口，断言后续接口查询到的字段内容与前面接口的写入值逐字段一致；链路需要的历史数据状态、多表联动前置条件由 SQL 前置数据脚本准备 |
| 接口基础面 | 单接口的正常路径（按 spec 请求结构传入合法值，验证 2xx 与响应结构）、边界（缺必填字段 → 4xx；空串/超长/类型错误等非法值 → 4xx；极值 → 正确响应或合理错误）与异常路径（非法状态跳转、重复提交与幂等、越权访问的拒绝）。基础面只作补充，不得替代链路 |
| 关键数据产出 | 涉及数据产出/落位/搬迁的变更，测试须断言关键产出字段已持久化到 spec 指定承载位置且值完整非空；产出承载位置包含数据库与缓存/中间件状态；产出为异步/延迟时须等待产出完成后断言；仅凭响应 2xx 与流程跑通不构成验收 |

业务链路清单的规模不是「每个变更接口一行」：一个接口可能出现在多条链路里，一条链路也可能不新增任何接口（既有入口被新的处理逻辑影响）。反过来，仅当链路覆盖到某个接口而该接口的入参校验、错误码、边界值尚无任何用例时，才补基础面用例。

链路的可观察结果不限于「接口返回成功」：链路末端须断言最终持久化状态（数据库字段值、缓存键值、消息入队与下游消费结果）与链路中的写入值一致。spec 描述为多个行为一并发生的（如状态变更与数据入队），每个行为都须有断言证据；断言范围不限于响应状态码与响应结构，须覆盖变更引发的真实行为（状态落库、消息入队、下游可消费等连带效果）。

### 四类覆盖划分界

四类容易互相顶替，按下表一次判清，不得互相替代：

| 维度 | 定义 | 缺了它就漏掉的区别 |
|------|------|------------------|
| 业务链路 | 跨多个接口、按业务顺序执行、断言后续查询字段内容与写入值逐字段一致的流程验证 | 单接口分别正确、串起来错（前序接口写入的状态被后续接口错误承接或不重算） |
| 接口基础面 | 单个接口在正常/边界/异常输入下的响应与错误处理验证 | 单接口的入参校验、错误码、边界值缺陷 |
| 一并操作行为组 | 同一请求内多个行为同时发生的断言（如状态变更 + 数据入队 + 审计落库） | 一个行为的断言被另一个行为的断言顶替，请求内实际只发生了一半 |
| 关键数据产出落位 | 产出字段在 spec 指定承载位置的持久化与完整性，含不暴露于响应、须异步等待的字段 | 响应正常但字段没落库、落错位置或值不完整 |

四类互补，均须覆盖。数据产出断言不得以「详情接口能查到」替代「字段已持久化到 spec 指定承载位置」；链路断言不得以「链路跑通」替代「字段值逐项一致」。

### 链路为空集的情形

仅当本次变更确无数据写入、无状态变化、无下游可见性时（典型形态：只改查询响应结构、只加入参校验、只改错误文案），才可判定无跨接口链路，此时以接口基础面为覆盖主体。

该判定须在链路映射中显式声明「无跨接口链路」并给出依据（写清变更点为何不产生写入/状态变化/下游可见性），不得以「接口太多没时间」或「本次只改一个接口」为由跳过链路段。

### 多写路径的顺序作用

同一份数据存在多条写入路径时（导入、保存、更新、批量同步等），链路须覆盖各路径的先后作用：前一路径写入的字段值（默认值、派生值、计算列）在后一路径执行后是否被重算、重置或保留，须按 spec 语义断言。

断言口径是「后一路径执行后再查一次」——先由路径 A 写入，再由路径 B 写入同一批数据，最后查询持久化状态逐字段核对；只验证两条路径各自成功，等于没有验证顺序作用。

## 数据模型搬迁与数据产出回归

字段/实体承载位置变更（如字段从子实体搬到实体根）时，测试须验证：新位置读写正常、旧位置无遗漏依赖/无残留写入、存量数据迁移后可读、关键产出字段非空完整、产出字段新旧承载位置映射正确；回归场景以同一输入比对关键数据产出与变更前基线一致（持久化存储快照/导出/读回结果对比）。

## 测试数据

http 请求体与 SQL 前置数据均按 spec 业务语义构造：使用真实字段值与业务含义明确的数据（如按 spec 字段语义构造的订单号、状态名、业务名称），禁止无意义占位值（如「测试数据」「aaa」「test1」）。列表/详情检索断言须基于真实业务标识（创建接口返回的 id/编码），使检索结果可预期、可追溯。

## 适用范围

涉及业务逻辑改动，且导致接口契约或数据口径变化时，属于 API 变更范围，MUST 执行本章所有后续约束。

以下情况不属于 API 变更，可豁免本章约束：
- 纯配置文件（非接口契约配置）、构建脚本、GitHub Actions、Docker 文件
- 仅 SQL init 文件改动且无 API 契约影响
- 涉及数据模型搬迁/存量数据迁移的 SQL 改动不适用「仅 SQL init 文件改动且无 API 契约影响」豁免
- 纯格式、注释、import 排序等无逻辑变更
- 仅测试代码变更（无生产代码、接口契约、构建与测试配置改动）
- 纯文档变更

按本章判定本次变更未涉及接口契约或数据口径时，脚本与执行两项交付物均不适用：以不适用申报并写清判定依据（如「本次变更未涉及接口契约或数据口径」）；判定适用时脚本必须就绪且必须实跑，不得以不适用之名跳过。

## 执行约束

MUST 遵守以下约束，不得以编译通过或单元测试通过替代 API 测试：

- MUST 不得以接口返回成功、状态字段正确或流程执行顺畅作为唯一验收；spec 含一并操作行为组时，须提供每个行为真实发生的断言证据。
- MUST 变更牵涉跨接口业务链路时，须按链路执行并提供链路尾部的字段级断言证据；以各接口单独跑通替代链路验证不构成验收。
- MUST 数据产出类变更须提供关键产出字段落位与完整性的断言证据（产出为异步/延迟时须等待产出完成后断言）。

### 脚本准备

本节交付脚本就绪证据。

MUST 确保 api-tests/script/ 目录下存在与本次 change 的业务链路清单及接口基础面对应的 .http 测试脚本：
- 链路已有对应脚本 → 更新为匹配变更后契约，并按链路顺序校核 `###` 块
- 链路尚无对应脚本 → 创建新脚本（不得因尚无已有脚本而跳过创建），同步准备 api-tests/data/ 下 SQL 前置数据脚本
- 接口基础面缺少用例的接口 → 补基础面块，并入所属链路的文件

### 链路映射

本节交付链路与脚本的对应记录：逐条列出业务链路 → 承载它的 .http 文件与 `###` 块，注明尾部断言落在哪个字段；随后列出接口基础面 → 文件与块。

无跨接口链路时，在链路映射中显式写「无跨接口链路」并给出依据（变更点为何不产生数据写入、状态变化或下游可见性），同时说明基础面覆盖了哪些接口。链路映射与脚本清单是同一份证据的两面，缺任一面视为脚本准备未完成。

### 脚本执行

本节交付脚本执行证据。

API 验证须通过 .http 兼容执行工具运行脚本——不得使用 curl、wget 等通用 HTTP 命令行工具替代。

#### 执行工具

API 测试脚本使用 IntelliJ HTTP Client CLI（`ijhttp`）执行，它是 JetBrains 官方提供的独立 CLI 工具，与 IDE 中 .http 文件的解析器和执行引擎完全一致。

- **工具**: `ijhttp`（IntelliJ HTTP Client CLI）
- **安装 (macOS)**: `brew install --cask ijhttp`
- **Docker**: `docker pull jetbrains/intellij-http-client`
- **直接下载**: `curl -f -L -o ijhttp.zip "https://jb.gg/ijhttp/latest"`
- **执行**: `ijhttp api-tests/script/<文件名>.http`
- **批量执行**: `ijhttp api-tests/script/*.http`
- **环境变量**: `ijhttp <文件> --env-file api-tests/http-client.env.json --env <环境名>`
- **测试报告 (JUnit XML)**: `ijhttp <文件>.http --report`
- **依赖**: 需 Java 17+（macOS 可用 `brew install --cask temurin` 安装）

API 验证须通过 `api-tests/script/` 下的 `.http` 脚本执行，不得使用 shell 命令或临时脚本替代。
