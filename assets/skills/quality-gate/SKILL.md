> **项目规范优先**：本 skill 所列约定为推荐标准。若项目已有明确规范且与本 skill 不一致，以项目规范为准。

## 检查流程（概览）

检查须按以下类别依次执行。每项不可跳跃——要么执行并报告结果，要么注明跳过理由：

| 序号 | 检查类别 | 含义 |
|------|---------|------|
| 0 | 工具环境检查 | 确保运行环境就绪，不可用则降级 |
| 1 | 编译检查 | 项目能否成功编译 |
| 2 | 代码格式检查 | 是否符合代码风格标准 |
| 3 | 架构约束检查 | 层间依赖、架构规则是否遵守 |
| 4 | 静态代码分析 | 代码质量规则（复杂度、错误模式等）|
| 5 | 单元测试 + 覆盖率 | 测试是否通过、覆盖是否达标 |
| 6 | 深度扫描 | 扩展静态分析（规则数量更多）。工具若存在独立类别的输出（独立端点、独立指标），每类均须获取并纳入检查结果，禁止默认只取单一类别 |
| 7 | 质量工具配置检查 | 质量门规则/配置未被弱化 |
| 8 | 降级/无基线口径 | 无法按变更来源归类时，全量扫描结果按统一 issue 结构、原始严重级别产出检查结果与 issue 清单，不区分是否本轮引入 |
| 9 | 汇总与产出 | 全部结果汇总为统一 issue 清单（含通过/不通过结论） |

具体工具的检查命令和输出解析由各技术栈对应的 quality-gate skill 提供。

## 0. 工具环境检查

在执行工具检查前，先确保工具运行环境就绪。环境检查失败时先按自愈性步骤尝试恢复；不可自愈或自愈失败后，提请用户处理或裁定。用户裁定降级跳过时，在报告中注明降级理由，不阻塞其他检查。

所有环境检查结果在报告中如实记录工具可用状态。具体处理方式由审查者按当前上下文判定。

## 1-6 确定性检查

每项检查的结果处理原则：

- **通过**：正常记录结果
- **不通过**：生成统一结构 issue，阻塞 task 完成

## 全量检查覆盖范围

执行全量确定性检查时，所有工具输出均须纳入检查结果与问题清单，不因文件不在本次变更范围或问题为存量而省略；存量问题按原严重级别处理。

## 失败定位

构建/检查失败时，失败的完整输出文本是定位全部失败项的唯一可靠依据；仅依据报错尾部数行做出修复决策会导致全量问题被遗漏并触发反复重试，视为不合规的故障处理方式。

## 7. 质量工具配置检查

检查本轮变更中是否包含质量工具规则/配置文件的改动。若包含，逐项检查：

- 规则是否被删除或降级
- 是否新增了过宽的 exclude/include 配置
- 质量工具插件配置是否被弱化（跳过执行、降低阻塞等级）
- 是否新增压制手段（代码内压制与配置压制）

配置无削弱 → 通过；存在削弱 → 工具层 issue。

### 7.1 压制识别与处理

- 压制形态（技术栈无关）：① 代码注解/属性级抑制；② 注释类抑制标记；③ 规则/文件排除配置（含规则移除、降级、过宽 exclude/include）；④ 平台状态标注；⑤ 构建/检查跳过开关。
- 处理要求：压制不消除问题本身，不得单独作为检查通过的依据；变更中新增的压制须附明确理由（压制处注释），由审查方判定其合理性；无理由或不合理的压制按原问题级别记录，且不得低于 Low 级。

## 8. 降级/无基线口径

SCM 数据不可用或历史基线不可靠时，扫描结果无法按变更来源归类，此时全量扫描结果同样按统一 issue 结构、按原始严重级别产出检查结果与 issue 清单，不区分是否本轮变更引入。

- 无法可靠归类的边界情况，按常规口径处理

## 9. 工具输出 → 统一 issue 结构

每个工具的输出必须翻译为统一 issue 结构：

```json
{
  "file": "<相对路径>",
  "line": <行号>,
  "dimension": "style|architecture|performance|security|maintainability",
  "severity": "Critical|High|Medium|Low|Info",
  "description": "<问题描述>",
  "suggestion": "<修改建议>"
}
```

各技术栈的 quality-gate skill 定义各自工具的输出到 dimension 和 severity 映射关系。

## 10. 汇总与产出

全部检查完成后，产出检查结果与 issue 清单（含通过/不通过结论）。
