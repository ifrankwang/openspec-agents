# 编排框架分析与优化

这套编排框架同时支持多个工具（harness）。分析和优化它时最容易出三个问题：需求没捋清就动手、方案写成用户看不懂的技术黑话、只按自己当前用的那一种工具考虑。本 skill 用「先捋清、再复核、后授权」的方式规避这三点。

## 入口

用户表达诉求后，主代理判定意图：

| 意图 | 信号 | 分析方法 |
|------|------|---------|
| 问题诊断 | 描述问题现象（卡住、反复报错、违反约束） | 5-Why 根因分析 |
| 改进优化 | 提出增强诉求（token 效率、加速、增加约束） | 现状-差距-方案分析 |
| 模糊 | 表述不清 | 用 question 工具向用户确认 |

## 统一流程：三道门 + 六个阶段

三道门互不替代，必须分别拿到：

| 门 | 位置 | 拿到什么 | 通过标志 |
|----|------|---------|---------|
| 门一 方案方向确认 | 访谈穷尽后 | 用户认可方案方向 | 用户对人话七要素摘要的自由文本确认 |
| 门二 实施授权 | 复核通过后 | 允许写文件的授权 | 用户明确说可以实施 |
| 门三 收尾确认 | 实施完成后 | 允许收尾发布 | 用户确认收尾 |

回答访谈问题、点头方案方向，都不等于允许写文件。门二必须单独拿到。

六个阶段按序推进：

1. 阶段一 先捋清楚（动笔前门禁）——走完到门一
2. 阶段二 按标准复核
3. 阶段三 实施授权门——走门二
4. 阶段四 输出人话报告
5. 阶段五 实施交接（仅授权后产出）
6. 阶段六 收尾确认门——走门三

### 阶段一：先捋清楚（动笔前门禁）

判意图 → 自己查证事实 → 决策树分轮访谈 → 关联场景清点 → 规则边界推演 → 门一。

**自己查证事实**：调研由主代理自己做，不拆成多个子代理各查各的。读当前代码（`src/core/`）、agent 定义（`assets/agents/`）、skill 定义（`assets/skills/`）、治理原则（`AGENTS.md`），提取约束清单。有 sessionID 时，按 session 证据流程分派**一个**子代理做导出与提取——这是工具执行场景，不是调研拆分。

**决策树分轮访谈**（方法论内联，不依赖任何外部工件或命令）：

- 先查证再问。能自己查到的事实不问用户；证据缺失、冲突或拿不到时，说明限制，只问推进所必需的那一点。
- 每轮把前置已定的问题一次问完（整条待决前沿），每题附推荐答案；答案依赖本轮未定问题的，放到下一轮。
- 一次一个聚焦问题，说明它为什么重要、解锁哪个决策；用户要求批量才批量，且保持小而相关。
- 挑战假设（自己的和用户的），必要时重构问题；不臆造意图、优先级或外部约束。
- 决策记在对话里，不落盘；已确认决策、建议默认值、未解决问题三者分开。沉默不是接受。

**关联场景清点**：访谈第一轮之前完成，作为决策树的输入，不是文档步骤。逐个列出会被这次改动影响的面并带证据：功能入口、被多入口复用的共享处理逻辑、下游数据消费者。每一个清点项都变成决策树分支，必须在访谈中让用户裁定「纳入 / 排除并说明原因」，前沿没清空不算捋清楚。

其中工具（harness）维度必须逐个清点，不能笼统写「全支持」：项目支持 5 种——Claude Code、Codex、ZCode、DeepSeek Harness、OpenCode。每一种都要作为独立问题让用户裁定本次纳入还是排除，并记录理由；只有用户明确说「全部覆盖」，才能全部纳入。

**规则边界推演**：对每条新增或修改的规则、校验、拦截，以及每个新增或重排的执行路径，逐条和用户推演三件事：

1. 判定条件与例外：什么情况必须拦，什么看着像但必须放行，给出最小拦截条件。
2. 合法反例：会被误拦的功能上合法场景，以及各自该怎么处理。
3. 等价执行路径与挂载点：同一业务意图有几条路径，检查挂在哪一层；判定必须挂在业务意图动作上，不能挂在别的流程复用的底层动作上。

若引入或重排执行路径，还要逐条过一遍既有规则，确认在新路径上该拦的仍拦、不该拦的不拦。

**顺序禁令**：访谈未穷尽（前沿非空、有关联场景缺用户裁定）时，禁止给出方案或让方案确认。每题附的推荐答案不是方案，不得冒充。用户中途索要方案，说明访谈还没结束，可以复述已定结论，但继续问到前沿清空。

**门一（HARD-GATE）**：访谈穷尽后，用**普通消息**（不用提问工具）给出人话七要素摘要，停下等用户自由文本回复。七要素都要有实质内容，不许两三句话糊过去：

1. 一句话讲清要做什么，然后把变更内容逐条用人话列出，每条是一句完整的话。
2. 是否触及外部约定。
3. 选定的方向，以及相对其它备选的取舍。
4. 人话分步讲清实施逻辑：数据或改动从哪来、经过什么处理、落到哪里、每条关联路径怎么适配。
5. 每个关联场景（含 5 种工具各自的裁定）纳入或排除及理由。
6. 受影响的能力。
7. 每条规则的边界裁定：拦截条件、必须放行的例外与合法反例、等价路径与挂载点。

回答访谈问题不算确认；确认必须是对这份摘要的直接回复。用户要改就改摘要并重提，直到明确确认。「太简单不用确认」不是跳过理由。确认结果记在对话里；若后续改动触及已确认方向，必须回到本门重走。

### 阶段二：按标准复核（唯一权威定义）

复核标准锁定为两项，不引入其它标准：

1. AGENTS.md 治理原则。
2. 生效闭环核验三项：
   - 强制生效机制：方案靠什么硬机制保证执行（门禁、校验、必做清单），还是仅提示词软约束？软约束不得宣称「保证生效」，只能写「期望生效」。
   - 绕过路径排查：哪些分支会让方案落空（整体豁免、失败短路、复核轮收敛口径、纯指令性要求）。
   - 连带同步面：工具文案与错误提示、视图渲染示例、测试硬编码清单、说明文档是否必须同步；漏列即完整性不通过。

执行方式：

- 把建议、治理原则、用户反馈打包，交给**唯一的复核子代理**；从头到尾复用这一个——本阶段、实施阶段的复核、以及各自的回环，都是同一个，不新开。
- 复核者独立、只报不改：只给结论，不改文档、不改代码、不提交。
- 复核内容：方案合理性、治理原则遵循、完整性、生效闭环三项。用户已确认不等于合理，方向性问题必须报出。
- 不通过就回退修改，再由同一个复核子代理复核；触及已确认方向时先回门一。
- 复核轮上限 3 次；超限停下，把遗留问题交给用户。

### 阶段三：实施授权门

复核通过后，请用户明确授权实施。方案方向点头、回答访谈问题，都不等于授权写文件。用户不实施就总结关键发现并结束；实施则把报告里的改进项清单加上用户的明确授权，作为进入实施流水线的交接载体。

### 阶段四：输出人话报告

给用户看的成果：纯人话、纯段落、不落盘。格式见「输出格式」。报告里不出现任何文件路径、行号、方法名、内部术语。

### 阶段五：实施交接（仅授权后产出）

拿到门二授权后才产出。它是独立产物，对象是实施子代理，内容必须精确，格式见「输出格式」。

### 阶段六：收尾确认门

实施完成后请用户确认，才进入收尾。这是第三道门，与门一、门二互不代替。流水线细节见实施流程（独立 skill）。

## 分析方法

- **5-Why 根因分析**：从问题表象逐层追问「为什么」，每层基于事实。落点必须是系统性根因——某段规范描述不清、某条指令缺乏约束力、某处校验有漏洞、某阶段缺少退出条件；不落个案操作失误。根因指向的文件要读对应章节交叉验证。只给根因结论，不展示追问链。
- **现状-差距-方案分析**：理解动机（复述确认，模糊则追问）→ 现状（基于已读文件）→ 目标状态 → 按维度拆差距 → 推荐方案（改动范围、生效机制与绕过路径、影响评估、风险权衡）。

两种方法的产出都只进人话报告；技术细节不进报告，只进实施交接。

## 输出格式（单一事实源）

两类产物必须分离：

| | 给用户的人话报告 | 给实施代理的交接 |
|---|---|---|
| 时机 | 随时可输出 | 仅门二授权后 |
| 对象 | 用户 | 实施子代理 |
| 语言 | 全篇大白话，零技术内容 | 精确：路径、行号、命中能力、清单、门禁 |

用户报告模板：

```
## 编排<问题诊断|优化项分析>报告

<有 session 时：一行人话说明来源>

### N. <问题简述>
大白话：3~5 句讲清问题是什么 / 要改什么 / 改完会怎样。
根因：<问题诊断用，结论>
现状与差距：<改进优化用，结论>
方案：<改动意图，纯人话>
```

报告全篇只用大白话，禁止文件路径、行号、方法名、内部术语；不写多级标题，不落盘。

实施交接模板（仅授权后）：

```
## 实施交接
### <实施项>
- 落点：文件路径 + 章节/行号
- 命中能力：按能力类别匹配的 skill（不硬编码名字）
- 必做清单：两种栈会话下各自实际展开项
- 视图与门禁：给出的具体要求
- 生效闭环核验：强制机制 / 绕过路径 / 连带同步面
- 影响评估：栈维度 + 工具维度的技术结论（见「影响评估」）
```

## 影响评估

一套改动常只在部分环境生效，不能从某一种环境直接推广。评估按两个正交维度逐项过：

1. **栈维度**：backend 会话、frontend 会话。共用层（workflow 配置、工具逻辑、agent 定义）两种会话都生效；栈专属层（按栈声明的能力、按栈分组的必做清单）只在命中的会话生效。逐项对照两种会话下命中哪些能力、必做清单展开成哪几项、视图与门禁要求是什么，以及各自要改的落点。
2. **工具维度**：项目支持的 5 种——Claude Code、Codex、ZCode、DeepSeek Harness、OpenCode。逐项确认改动在每种工具下是否生效、差异在哪、各自等价的实现位置是什么。

两个维度的结论都分两版输出：**人话版**并入用户报告对应项的「方案」小节（只讲哪些环境会受影响、哪些不会，不展开技术细节）；**技术版**放进实施交接的「影响评估」。两版结论都不在各自产物里单开章节。

## 约束与简洁输出

- 分析阶段不修改文件；实施阶段仅子代理改文件，主代理不得直接 edit/write。
- 5-Why 必须落到系统性根因。
- 有 sessionID 时，证据导出与提取由子代理执行，主代理不直接跑导出脚本或读原始 session 数据。
- 工具逻辑以源码为准；声明式行为与运行时行为可能有差异。
- 少派子代理：调研主代理自己做，不拆分；复核全程复用同一个子代理，不新开；session 导出属于工具执行场景，单独分派一个子代理。
- 方法论内联，用能力类别描述；不点名其它 skill，不引用任何 schema 或工件路径。
- 技术细节只放实施交接，不放用户报告。
- 结论至上：只输出问题与方案，不展示分析过程；扁平结构，不深嵌套；引用不赘述。
- 风险如实写：访谈会增加轮次；访谈若用技术语言，方案的人话诉求就落空；三道门混淆会导致误授权写文件或误收尾。
