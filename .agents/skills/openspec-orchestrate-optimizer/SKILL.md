# 编排框架分析与优化

## 入口

用户表达诉求后，主代理判定意图：

| 意图 | 信号 | 分析方法 |
|------|------|---------|
| 问题诊断 | 描述问题现象（卡住、反复报错、违反约束） | 5-Why 根因分析 |
| 改进优化 | 提出增强诉求（token 效率、加速、增加约束） | 现状-差距-方案分析 |
| 模糊 | 表述不清 | 用 question 工具向用户确认 |

## 统一流程

1. **明确意图** — 按入口表判定，模糊则追问
2. **收集证据** — 读当前代码（`src/tools/`）、agent 定义（`assets/agents/`）、skill 定义（`assets/skills/`）、治理原则（`AGENTS.md`）。有 sessionID 则导出 session 比对（见 `reference/session-evidence.md`）
3. **分析** — 按意图执行对应分析方法
4. **方案复核** — 分派独立子代理交叉验证方案合理性、治理原则遵循、完整性。违规则回退
5. **输出报告** — 纯段落，不落盘
6. **实施**（可选）— 用户确认后按 `reference/implementation.md` 执行

## 分析方法

### 5-Why 根因分析

从问题表象逐层追问"为什么"，每层基于事实（文件内容、约束清单）。最终落点必须是系统性根因——skill 某章节描述不清、agent 指令缺乏约束力、工具校验有漏洞、阶段缺少退出条件。不落个案操作失误。根因指向文件须读对应章节交叉验证。

### 现状-差距-方案分析

1. 理解优化动机（复述确认，模糊则追问）
2. 现状分析（基于已读文件的当前实现）
3. 目标状态（基于动机描述期望状态）
4. 差距识别（按维度拆解 gap）
5. 推荐方案（改动范围 + 影响评估 + 风险权衡）

## 方案复核

拟定建议后、输出前执行：
1. 建议 + AGENTS.md 治理原则 + 用户反馈打包
2. 分派全新子代理
3. 复核：方案合理性、治理原则遵循、完整性
4. 通过→输出；违规→回退

## 输出格式

```
## 编排<会话分析|优化项分析>报告
<**Session**: <ID> — 有 session 时出现>

### N. <问题简述>
#### 根因                        ← 问题诊断用
<结论>

#### 现状与差距                  ← 改进优化用
<结论>

#### 方案
<改动意图（含文件路径和章节/行号）>
```

## session 证据

sessionID 只在有助于精确定位根因或验证行为偏差时使用。导出与事件提取方法见 `reference/session-evidence.md`。无 sessionID 时纯基于当前代码和文档分析。

## 约束

- 分析阶段不修改文件；实施阶段仅子代理改文件，主代理不得直接改
- 改进建议必须指名具体文件路径和章节/行号
- 5-Why 必须落到系统性根因
- 子代理只负责数据提取，主代理负责分析与判断
- 工具逻辑以源码为准，但声明式行为与运行时行为可能有差异

## 简洁输出原则

- 结论至上：只输出问题与方案，不展示分析过程。5-Why 只给根因结论，不给追问链条
- 扁平结构：不使用多层章节嵌套
- 引用不赘述
